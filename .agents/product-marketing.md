## Product Overview

**One-liner:** Vue 3 的组织架构树 / OKR 树组件——根节点左右双向展开，连接线纯 CSS 绘制。

**What it does:** 渲染"中心根节点 + 左右两侧同时展开子树"的层级图（飞书 OKR 那种布局），
内建折叠动画、复选框父子联动、拖拽换父级、懒加载、虚拟滚动、画布缩放与 PNG/SVG 导出；
外观全部走 `--okr-*` CSS 变量，内置六套主题。API 与 Vue 2 时代的前身 `vue-okr-tree` 对齐，
迁移不重写模板。

**Product category:** Vue 3 组件库 › 树形 / 层级可视化组件（组织架构图 · OKR 目标树）。
使用者搜的是："vue3 组织架构图 组件"、"vue 树形组件"、"org chart vue3"、"okr tree"。

**Product type:** 开源 npm 包（MIT，ESM / CJS / UMD + `style.css` + 完整 `.d.ts`，零运行时依赖）。

**Business model:** 免费。真实 KPI 是 GitHub star 与 npm 下载量，二者都是**发现性问题**，
不是产品能力问题（见 Goals 一节的现状对比）。

## Target Audience

**Target companies:** 用 Vue 3 的中后台团队，国内为主（中文文档站、ICP 备案域名）；
React 侧走姊妹包 `react-okr-tree`。

**Decision-makers:** 前端开发者个人（自下而上：先在自己的页面试一下）→ 前端负责人
（拍板：维护成本、包体、类型、有没有人管）。**对开源库来说"决策者"常常是同一个人。**

**Primary use case:** 页面上要画"一个中心节点向左右两边铺开"的层级图——组织架构 / 通讯录
可视化、OKR / 目标树、审批层级、股权结构。通用树组件只能做成单向缩进列表，做不出这种版式。

**Jobs to be done:**

- 让我的页面在两小时内出现一张能看、能折叠、能改报错的组织架构图。
- 从 Vue 2 的前身 `vue-okr-tree` 迁过来时，不要重写模板和事件。
- 数据量大时不要卡死（懒加载 / 虚拟滚动），需要出图时能导 PNG。

**Use cases:**

- 企业组织架构 / 部门树（左右展开，节点卡片自定内容）
- 飞书式 OKR 目标树（左右对齐、折叠不位移）
- 多层审批 / 分佣 / 股权结构图
- 需要拖拽改父级的层级编辑器

## Problems & Pain Points

**Core problem:** 通用树组件解决的是"单向缩进的层级列表"，而组织架构图 / OKR 树需要
**根居中、左右铺开、根对齐**的二维布局——通用组件根本不做这件事。

**Why alternatives fall short（只描述做法，不点名产品）：**

- **用通用树组件硬凑**：只能单向缩进；要双向就得两棵树 + 自己画连线 + 自己算对齐。
- **自己用 SVG / Canvas / 图库画**：连线、根对齐、折叠动画、拖拽落点、缩放平移，每一项都是单独的坑。
- **停在 Vue 2 的前身**：确实有这个版式，但 Vue 3 项目直接不可用（作者 2026-11-25 确认已半停更）。

**What it costs them:** 自己糊一套 300–1000 行；后续交互（拖拽、懒加载、导出）每加一项再翻一次。
选错方案的成本是"上线后样式/行为改不动，但换组件要重画"。

**Emotional tension:** 组件库里的一个"看图组件"通常不是核心业务，却最容易被产品经理反复改版式；
开发者想要的是"一次接好、别再找我"。

## Differentiation

**Key differentiators:**

- **左右双向展开 + 根对齐**：`align-root` 让根节点在折叠/展开时**不位移**，不需要手动量 DOM——这是"飞书 OKR 布局"的核心手感，通用树组件做不到。
- **纯 CSS 连线**（另有 SVG 模式）：不依赖 canvas / 图库 / 任何布局引擎，节点就是普通 DOM（可以被 CSS、被 Tailwind、被选中复制）。
- **零运行时依赖、约 20 kB gzip**，ESM/CJS/UMD + 完整 `.d.ts`。
- **外观全量可覆写**：六套内置主题（default / feishu / dark / auto / minimal / colorful）+ `--okr-*` 变量 + `unstyled` 交给 Tailwind。
- **大数据量友好**：`lazy` + `load` 只加载展开路径；`virtual` 窗口化渲染；`OkrTreeViewport` 滚轮缩放 / 拖拽平移 / 导出 PNG、SVG。
- **可访问性做到位**：WAI-ARIA tree 语义、漫游 tabindex、方向键、自动响应减弱动效。
- **迁移成本≈0**：API 与前身 `vue-okr-tree` 对齐，并修掉了原版的多根过滤、左右树同 key 覆盖、`animate` 无效等缺陷。
- **双框架锁步**：`react-okr-tree` 同号发版，同一个团队跨栈复用不用学两套 API。

**How we do it differently:** 把"一张组织架构图需要的所有交互"一次性做完（折叠、勾选、拖拽、
懒加载、虚拟滚动、缩放导出），而不是给一个可组合的底层原语让人自己拼。

**Why that's better:** 使用者的真实成本不在"渲染一颗树"，而在"交互一项项加"。

**Why users pick us（2026-11-25：作者确认目前只有自己的项目在用，无公开用户证言）：**
现阶段可信的替代是"工程事实"——307 条单测、视觉基线、产物 d.ts 在 Vue 3.5.2 下限上真实编译、
逐版 CHANGELOG。**不要编造用户案例或证言。**

## Switching Dynamics

**Push（离开现状的推力）：** 自己糊的 SVG 连线改第三版时已经没人敢动；Vue 2 老项目升级后
前身直接报错（且已半停更）。
**Pull（被吸引的点）：** Playground 里能直接改数据看到效果；迁移页给出 API 对照；"根对齐不位移"这一条就能说服做过这个版式的人。
**Habit（留下的惯性）：** 已经在用的树组件 API 熟了、组件库集成了、样式系统也统一了。
**Anxiety（切换的担忧）：** 小包跑路、文档不全、和我现有样式体系打架、出问题没人回。

> 对 star / 下载目标而言，**Habit 与 Anxiety 是主要阻力**，Push 与 Pull 已经成立（产品本身做得比体量好）。
> 所以营销动作的重心是"降低尝试成本"（可复制的最小示例、可搜索的文档页、清晰的支持面），
> 而不是继续加功能。
